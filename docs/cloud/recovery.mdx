---
title: Recovery insights
description: Cloud can show that a run recovered. The device still performs the recovery.
---

`WORKFLOW_RECOVERED` is the native event for a run that resumed in a new process. The payload can say whether it continued from an interruption or from a pause, and which step was current. That event is metadata. Replaying it in Cloud does not resume the agent.

Recovery still requires the application to open the same database and call `runtime.resume`. See [Crash recovery](/concepts/crash-recovery).

If the process dies after the exporter stores a batch and before the cursor advances, the next flush sends the same `batchId` and the same event ids. Cloud treats that as a replay, not as a second run.

A run that Cloud has expired, or a history conflict for a new batch, stays on the device. The local journal is not deleted to satisfy the collector. In the current default branch, a permanent rejection is remembered for that destination so the exporter does not rediscover it forever. npm {{sdkVersion}} holds the destination on those responses instead. See [Troubleshooting](/cloud/troubleshooting).

Cloud retention does not delete local SQLite. A 14-day Cloud window, when that is the policy of the deployed service, applies to stored observations, not to the device.
